# MATH-174 — `source_chunk=1` exact workload independence audit

Date: 2026-09-16

## Classification

`SIDE / SUPPORT ONLY`

This audit fixes the execution meaning of the MATH-161/MATH-166/MATH-171 fragmented-shard workflows. It changes no source set and makes no closure claim.

## MATH-108 ingestion semantics

In the unchanged MATH-108 engine, every input row is appended to `chunk`. When

```text
chunk.size() == source_chunk
```

holds, the engine immediately calls

```text
audit(std::move(chunk), stats)
```

then clears the chunk before reading later source rows.

The fragmented workflows explicitly invoke the engine with

```text
source_chunk = 1.
```

Therefore each input AP row enters `audit()` alone. Different input rows in the same matrix job are never normalized, merged, state-propagated, or resource-bisected together.

## Exact consequence

For a subshard containing `k` source rows under `source_chunk=1`, execution is an ordered sequence of `k` independent exact AP audits sharing only the aggregate `Stats` object.

For each row independently:

1. `normalize()` receives that row alone;
2. `advance()` evolves only the exact state generated by that row;
3. if `STATE_CAP` is exceeded and the raw source list has one row, MATH-108 bisects that AP's parameter interval exactly;
4. successful leaves add that row/child's exact occurrence mass to the global closed-mass counter.

The final executable-level invariant remains

```text
closed_occurrence_mass == total_occurrences.
```

Thus there is no cross-row heuristic pruning or cross-row state interaction.

## Composite-tail interpretation

For MATH-161 shard 18:

```text
subshards 0..46   1 AP row/job
subshards 47..63  136..146 AP rows/job
source_chunk       1
```

Hence each composite-tail job is not one 136..146-AP dynamical union state. It is 136..146 independent exact AP audits executed sequentially in one GitHub job.

Its wall time is therefore an aggregate execution cost over those independent AP rows. MATH-167 shows that this cost cannot be predicted from occurrence mass alone.

## Recursive256 implication

MATH-173 shows that across every fragmented original shard, recursive256 reduces

```text
max AP rows/subshard:
64-way   up to 244
256-way  up to 95
```

and reduces the exact occurrence cap from

```text
3,363,923,805 -> 840,980,952.
```

Under `source_chunk=1`, these changes reduce both the maximum represented mass per matrix job and the maximum number of independent AP audits accumulated inside one job.

Across all 114 fragmented original shards, the per-shard maximum row-packing bound improves under recursive256; the observed static reduction in `max pieces/subshard` is approximately `43.94%..61.07%`, while emitted split-piece count rises only about `6.94%..7.13%` per original shard.

## Scheduling consequence

A fragmented-job timeout should be diagnosed at two levels:

```text
single-row cost       AP-specific exact state-evolution geometry
job accumulation      sum of many independent row audits
```

Recursive256 can improve the second level and can also further split high-multiplicity AP rows, but it cannot guarantee a particular wall time because a single exact AP may still have difficult state geometry.

Accordingly, no automatic runtime threshold is promoted from MATH-174. Actual composite-tail measurements remain necessary.

## Claim boundary

MATH-174 is an execution-semantics and scheduling audit only. It closes no source mass and proves no new Collatz statement.
